# Как мы работаем с ботом

Этот файл является главным описанием запуска и изменений. Если другой документ ему противоречит, используем этот файл.

## Единая схема

- GitHub хранит единственную актуальную версию кода: `main`.
- Production-бот для всех тестовых пользователей запускается в одном облачном Background Worker.
- Один Telegram-токен = один запущенный Worker.
- Mac не запускает production-бота.
- Локальный запуск используется только с отдельным тестовым ботом и отдельным токеном BotFather.
- `trecker.db` не переносим между компьютером и production вручную.

## Решение по хостингу

Единственный production-хостинг проекта — Railway. Локальный Mac не является
production-сервером и не запускается с production-токеном. Не создаём второй
хостинг и не переносим проект между платформами для отдельных правок.

Если Railway не подтянул новый commit, исправляем настройки GitHub-репозитория или
делаем ручной Redeploy в Railway. Это не повод запускать второй polling-процесс.

Обязательные настройки production:

- источник: GitHub-репозиторий `manastasiya-beep/emotional-tracker`;
- ветка: `main`;
- команда запуска: `python main.py`;
- переменная окружения: `BOT_TOKEN`;
- число реплик/worker: `1`;
- автоматический deploy после push в `main`;
- после deploy проверяем, что запущен commit, который только что отправили.

При первоначальной настройке Railway нужно один раз проверить: подключён именно
этот репозиторий, выбрана ветка `main`, включён автоматический deploy и запущен
ровно один Worker.

## Как публиковать изменение

1. Вносим изменение в код.
2. Запускаем проверку:
   ```bash
   python3 -m py_compile main.py db.py config.py keyboards.py rewards.py
   ```
3. Если изменение касается сценариев пользователя, проходим `REGRESSION_CHECKLIST.md` на отдельном тестовом боте.
4. Отправляем изменения в GitHub:
   ```bash
   git add <изменённые файлы>
   git commit -m "Короткое описание изменения"
   git push origin main
   ```
5. Ждём один успешный deployment в production.
6. Проверяем production-сценарий в Telegram.

До успешной проверки deployment не запускаем `python main.py` локально с production-токеном.

## Как проверять состояние

Перед диагностикой смотрим только три места:

1. GitHub: последний commit в ветке `main`.
2. Хостинг: один активный Worker и тот же commit.
3. Логи Worker: нет `Conflict: terminated by other getUpdates request`.

Если есть `Conflict`, останавливаем локальные процессы командой:

```bash
pkill -9 -f "main.py"
```

Затем проверяем, что на хостинге остался только один Worker. Не запускаем несколько команд `python main.py` в разных терминалах.

## Как тестировать локально

Для локальной разработки нужен отдельный бот в BotFather:

- production-токен остаётся только в облачном Worker;
- тестовый токен хранится в локальном `.env` как `BOT_TOKEN`;
- тестеры не используют локальный бот;
- перед публикацией проверяем изменения на тестовом боте, после публикации повторяем короткую проверку в production.

Если отдельного тестового бота пока нет, локальный запуск не используем: сначала проверяем изменение после одного production deployment.

## Добавление картин

Картины добавляются в `config.py` в список `PAINTINGS`. Для 100, 200 и 500 картин отдельная программа не нужна. После добавления:

1. проверить, что у каждой картины есть `id`, `zone`, `title`, `artist`, `url`;
2. выполнить проверку компиляции;
3. сделать один commit и push;
4. дождаться одного deployment;
5. проверить отправку картины в Telegram.

## Что не делаем

- не запускаем один токен одновременно локально и в облаке;
- не создаём второй Worker для того же бота;
- не меняем хостинг для каждой отдельной правки;
- не считаем локальный `trecker.db` production-базой;
- не проверяем изменения по старому сообщению или старому deployment.

## Источник правды по файлам

- `OPERATING_GUIDE.md` — как запускать и публиковать изменения;
- `REGRESSION_CHECKLIST.md` — что проверять после изменений;
- `README.md` — краткое описание проекта;
- `config.py` — картины, вопросы и тексты конфигурации;
- `main.py` — логика бота.
